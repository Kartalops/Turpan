## Feature Details

### 1. `--fail-on` Exit Code Policy

**Added to `turpan review` and `turpan review-diff`:**

```bash
turpan review . --from main --to HEAD --fail-on critical   # exit 1 if any critical
turpan review . --from main --to HEAD --fail-on high       # exit 1 if critical or high
turpan review . --from main --to HEAD --fail-on never       # never fail (default)
```

**Logic:**
- `fail-on=critical` → exit 1 when `critical ≥ 1`
- `fail-on=high` → exit 1 when `critical ≥ 1` or `high ≥ 1`
- `fail-on=never` → always exit 0 (default)
- Analysis errors (network, etc.) always exit non-zero, independent of `--fail-on`

### 2. GitHub Action Package

**Location:** `.github/actions/turpan-review/`

**Inputs:**
- `project-path` — path to review (default `.`)
- `base-ref` — base branch for diff (default `main`)
- `head-ref` — head branch for diff (default `HEAD`)
- `review-mode` — `quick` or `deep` (default `quick`)
- `ui-enabled` — enable UI analysis (default `false`)
- `dep-audit-enabled` — enable dependency audit (default `false`)
- `fail-on` — `critical | high | never` (default `never`)
- `post-comment` — post PR comment (default `false`)
- `update-comment` — update existing sticky comment (default `true`)
- `turpan-version` — version/dist-tag (default `latest`)

**Outputs:**
- `verdict` — GO / CONDITIONAL_GO / NO_GO
- `score` — overall score 0-100
- `critical-count` — number of critical findings
- `high-count` — number of high findings

### 3. Example PR Review Workflow

**Location:** `.github/workflows/turpan-pr-review.yml.example`

Pattern includes:
- `actions/checkout@v4` with `fetch-depth: 0` for diff analysis
- Node.js + pnpm setup with caching
- `pnpm build` to build Turpan
- Diff ref detection (handles `pull_request` event and `workflow_dispatch`)
- `turpan review . --from $BASE --to $HEAD --fail-on $FAIL_ON`
- Artifact upload via `actions/upload-artifact@v4`
- GitHub step summary with verdict/score/counts table
- Optional PR comment posting via `turpan scripts post-pr-comment`
- Exit code policy enforcement step

### 4. Sticky PR Comment Script

**Command:** `turpan scripts post-pr-comment --run-path <dir> --pr-number <num> [--dry-run]`

**Features:**
- Reads `TURPAN_PR_COMMENT.md` from the run path
- Redacts secrets before posting (Bearer tokens, API keys, env vars, embedded credentials)
- Truncates comments > 65,536 chars with artifact reference
- Wraps with sticky marker `<!-- turpan-pr-review sticky comment -->`
- Detects and updates existing sticky comment (or posts new)
- `--dry-run` mode for preview without posting
- Uses `GITHUB_TOKEN` from environment (no token printed)

## Security Notes

1. **No secrets in comments** — `redactSecrets()` scrubs:
   - Bearer tokens → `Bearer [REDACTED]`
   - Long hex strings (API keys) → `[REDACTED_KEY]`
   - Env var values in code blocks → `[REDACTED]`
   - URLs with embedded credentials → `https://[REDACTED]@`
   - Long base64 strings → `[REDACTED_SECRET]`

2. **Token never logged** — `GITHUB_TOKEN` used only in fetch headers

3. **Comment size limit** — GitHub caps at 65,536 chars; truncated with artifact reference

4. **No artifact path exposure** — internal paths not exposed in public-facing outputs

## Public Beta Impact

This feature enables Turpan to be used as an automated PR check in CI/CD pipelines:

- **No secrets required** for basic use (artifact-only mode)
- **Optional PR comments** require only `GITHUB_TOKEN` (provided automatically by GitHub Actions)
- **Fail-on policies** give teams control over merge gates without changing analyzer behavior
- **Artifact uploads** preserve full reports even when `--fail-on never` is used

Teams adopting this should:
1. Start with `--fail-on never` to observe baseline finding rates
2. Graduate to `--fail-on critical` once false-positive rates are understood
3. Consider `--fail-on high` only for high-confidence, low-noise codebases
